\lstinputlisting[caption={第一个可运行的 C++ 程序}]{code/ch01/first_program.cpp}

\subsection{逐行读取程序结构}

\texttt{\#include <iostream>} 是预处理指令。行首的 \texttt{\#} 表示它在正式编译前处理；尖括号中的 \texttt{iostream} 是标准库头文件名，它让当前源文件看见标准输入输出工具的声明。这一行末尾没有分号，因为它不是 C++ 语句。

\texttt{int main()} 声明程序入口。这里先把 \texttt{int} 理解为“该入口会交回一个整数状态”，\texttt{main} 是标准规定的名称，空圆括号表示本版本暂不接收命令行参数。左花括号 \texttt{\{} 开始函数体，匹配的右花括号 \texttt{\}} 结束函数体；缩进帮助人阅读，但花括号才决定结构。

\texttt{//} 从当前位置开始一行注释；\texttt{/*} 与 \texttt{*/} 则界定可以跨行的块注释。编译器不会把注释内容当作要执行的语句，但块注释不能嵌套：遇到第一个 \texttt{*/} 就已经结束，因此它不适合包住本身含块注释的代码。\texttt{std::cout} 是标准输出流；\texttt{std::} 指明名称属于标准库命名空间，双冒号是作用域解析符。\texttt{<<} 把右侧内容送入输出流，双引号包住要输出的文本，\texttt{\textbackslash n} 表示换行。字符串和数字的正式类型留到第 2 章，本章只要求能正确识读这条输出语句。

行尾的分号结束一条 C++ 语句。\texttt{return 0;} 把成功状态交回运行环境；在 Linux/WSL 中，状态 0 约定为成功，非零表示失败。分号、圆括号、花括号和引号都是语法的一部分，不能像 Python 中某些可选标点那样随意删去。

\begin{pythonbridge}
Python 的缩进同时承担语法结构，\texttt{print()} 由运行时按名称查找。C++ 用花括号划分函数体，用分号结束语句，并在编译阶段解析 \texttt{std::cout}。两者都能向终端输出文本，但程序如何到达“可运行”状态并不等价。

\pythoncompare{Python 用缩进和 print；C++ 用花括号、分号与 std::cout。}{本例没有借用输入；标准流由运行时管理，局部对象按作用域结束。}{Python 在执行到名称时检查；C++ 在编译期解析名称与表达式类型。}{Python 可能运行到此才报 NameError；C++ 先给编译或链接诊断。}
\end{pythonbridge}

\subsection{动手验证}

先只把源码中的 \texttt{//} 注释改成单行的 \texttt{/* ... */} 注释，预测输出应逐字符不变，再构建运行；块注释须保持非嵌套。然后只把输出文本改为 \texttt{quant-cpp-learning}，预测哪一行会变化并再次运行。若只改文本却出现语法错误，优先检查成对双引号、末尾分号和 \texttt{\textbackslash n} 是否仍在；完成后恢复章首约定输出，确保精确测试重新通过。

\section{单文件命令与构建流水线}

\subsection{从空目录运行 GCC 主线}

在 Linux 或 WSL 中创建目录，用编辑器把清单保存为 \path{first_program.cpp}，然后运行：

\begin{lstlisting}[language=bash,numbers=none]
mkdir ch01-first-build
cd ch01-first-build
g++ -std=c++20 -Wall -Wextra -Wpedantic \
    first_program.cpp -o first_program
./first_program
echo $?
\end{lstlisting}

\texttt{g++} 是 GCC 的 C++ 驱动程序；\texttt{-std=c++20} 选择本书语言版本；三个警告选项要求编译器报告常见可疑代码；\texttt{-o first\_program} 指定输出文件名。反斜杠位于 shell 行末时表示命令在下一行继续，不属于源文件内容。\texttt{./} 明确运行当前目录中的文件，\texttt{echo \$?} 查看刚结束程序的状态，应为 0。

一条 \texttt{g++} 命令隐藏了多步流水线：
\[
\text{source} \longrightarrow \text{preprocess} \longrightarrow
\text{compile} \longrightarrow \text{object file} \longrightarrow
\text{link} \longrightarrow \text{executable} \longrightarrow \text{run}.
\]

预处理展开 \texttt{\#include} 等指令；编译器检查当前翻译单元并产生目标文件；链接器把目标文件和所需库组合为可执行文件；只有最后一步才真正启动你的程序。想观察中间边界，可把命令拆开：

\begin{lstlisting}[language=bash,numbers=none]
g++ -std=c++20 -Wall -Wextra -Wpedantic \
    -c first_program.cpp -o first_program.o
g++ first_program.o -o first_program
./first_program
\end{lstlisting}

\texttt{-c} 表示只编译、不链接，所以第一条命令成功只能证明目标文件已经生成，不能证明最终程序的所有名称都有定义。

\paragraph{与 Python 对照。}
导入 Python 模块也可能失败，但普通 Python 工作流不会先生成目标文件再调用链接器。C++ 的阶段边界使一部分错误更早暴露，也要求你看清究竟是哪条命令失败，不能把所有诊断笼统归为“编译不过”。

\section{三个故障实验：先分类，再修复}

故意失败源码都隔离在 \path{code/ch01/failures/}，不进入默认绿色构建。每个实验只验收稳定类别和非零状态，不绑定某一版 GCC 的完整英文句子。

\subsection{编译失败：缺少分号}

\path{missing_semicolon.cpp} 的输出语句末尾故意少了分号：

\begin{lstlisting}
std::cout << "quant-cpp-ready\n"
return 0;
\end{lstlisting}

运行 \path{g++ -std=c++20 -c code/ch01/failures/missing_semicolon.cpp}。编译器会在读到 \texttt{return} 附近报告“期望分号”类别；箭头位置可能落在下一行，因为解析器直到看到下一个记号才确认上一条语句没有结束。根因是语法不完整，修复是在输出语句后恢复分号。

\subsection{链接失败：声明存在，定义缺失}

\path{missing_definition.cpp} 包含一个函数声明和一次调用，但项目没有提供函数体：

\begin{lstlisting}
double expected_notional();  // declaration only
// main later calls expected_notional()
\end{lstlisting}

先用 \texttt{-c} 生成目标文件会成功，因为当前文件已经知道调用的名称和返回类型；再运行：

\begin{lstlisting}[language=bash,numbers=none]
g++ missing_definition.o -o missing_definition
\end{lstlisting}

链接器应报告 \texttt{undefined reference} 类别。函数声明与定义会在第 3 章从零教学；此处只建立诊断规则：能产生 \texttt{.o} 但不能产生可执行文件，问题就在链接阶段。修复方式是提供唯一定义并让它参与链接；反复修改编译警告选项无助于补齐定义。

\subsection{运行期失败：程序主动报告启动错误}

\path{startup_failure.cpp} 可以成功编译和链接，但启动后把错误写到 \texttt{std::cerr}，再 \texttt{return 2;}：

\begin{lstlisting}
std::cerr << "startup-error: market-data path is required\n";
return 2;
\end{lstlisting}

这模拟量化程序在启动检查中发现缺少行情路径。\texttt{std::cerr} 是标准错误流，便于把诊断与正常结果分开；状态 2 是本实验定义的失败协议。若可执行文件已经启动并打印上述消息，故障就发生在运行期，链接阶段此前已经完成。

\subsection{诊断记录模板：从首个根因开始}

编译器和链接器可能在一个根因后产生许多级联消息。可靠记录按固定顺序写五项：当前目录与完整命令；第一条非零退出的命令；失败前最后生成的产物；第一条能够解释后续消息的诊断；修复后重跑的命令和结果。只截取终端末尾一句，常会丢掉真正的文件名、行号和阶段。

阶段也能由产物反推：没有目标文件，先查预处理或编译；已有 \texttt{.o} 而没有可执行文件，查链接；已有可执行文件并且程序已经输出诊断，查运行期输入或业务状态。若旧产物仍在，先删除它或换用全新构建目录，避免把昨日成功生成的文件误当成今日命令的证据。

\section{最小 CMake 目标与干净构建}

手写 GCC 命令适合学习阶段边界；项目增长后，应用 CMake 描述“要构建什么”。下面的文件与第一个程序放在同一目录，并参与本项目的干净构建测试：

\lstinputlisting[caption={第一个最小 CMake 项目},language=bash]{code/ch01/CMakeLists.txt}

\texttt{cmake\_minimum\_required} 声明最低 CMake 版本；\texttt{project} 建立一个使用 C++ 的项目；三个 \texttt{set} 选择 C++20、要求编译器支持它并关闭厂商扩展；\texttt{add\_executable} 创建名为 \texttt{ch01\_first\_program} 的目标，并把源文件交给它。

在包含这两个文件的项目目录中运行：

\begin{lstlisting}[language=bash,numbers=none]
cmake -S . -B build
cmake --build build --target ch01_first_program
./build/ch01_first_program
\end{lstlisting}

\texttt{-S .} 指定源目录，\texttt{-B build} 指定目录外构建树；源码与生成文件因此不会混在一起。第一次运行前 \path{build/} 不应存在，这叫干净构建。若只删除可执行文件而保留旧缓存，不能证明项目从零可配置。验收完成后可删除整个 \path{build/}，再重复三条命令。

\paragraph{与 Python 对照。}
Python 项目常用 \path{pyproject.toml} 描述包、用虚拟环境隔离依赖，并由解释器直接运行入口；这里的 \path{CMakeLists.txt} 描述原生构建目标。\texttt{cmake -S . -B build} 只读取项目并生成当前平台的构建系统，不会运行程序；\texttt{cmake --build build} 才调用编译器与链接器。CMake 因而是跨平台的构建描述层，与 C++ 解释器或包管理器承担不同职责。

做一次只有一个变量的失败练习：在项目副本里只把 \texttt{add\_executable} 中的 \path{first_program.cpp} 改为不存在的 \path{missing.cpp}，并把配置输出写入全新的 \path{build-broken/}。预期 \texttt{cmake -S . -B build-broken} 在配置或生成阶段以非零状态结束，稳定类别是 \texttt{Cannot find source file}，而且不会产生可运行目标。把文件名恢复后删除 \path{build-broken/}，从空构建目录重跑配置、构建和程序；若仍失败，先核对源目录是否同时包含清单中的两个文件，再读第一条 CMake 诊断。此类配置错误与编译器选项无关。

\subsection{Windows 差异只放在命令边缘}

正文主线使用 Linux/WSL 与 GCC。在 PowerShell 中，CMake 的前两条命令保持不变；单配置生成器的程序通常写作 \path{.\build\ch01_first_program.exe}，Visual Studio 等多配置生成器可能位于 \path{build\Debug}。直接使用 MSVC 时警告选项是 \texttt{/W4 /permissive-}；MSVC 不接受 GCC 的 \texttt{-Wall -Wextra -Wpedantic}。本书只维护一套教学主线：以 \texttt{cmake --build} 屏蔽生成器细节，需要 Linux sanitizer 或书中精确 shell 命令时使用 WSL。

\section{章末三层练习}

\subsection*{随堂验证汇总}

\begin{enumerate}
  \item 只删除 \texttt{return 0;} 后的分号，比较首个诊断位置，然后恢复文件。
  \item 分别记录两条命令的退出状态，确认前者为 0、后者非零。
  \item 只把状态改为 3，运行后用 \texttt{echo \$?} 验证；随后恢复为 2，使自动验收重新通过。
  \item 为三个实验各写一行“命令 → 最后产物 → 退出状态 → 稳定类别”。三行应分别停在源码、目标文件和已启动进程处；若分类只写“报错”，还没有完成诊断。
\end{enumerate}

\begin{enumerate}
  \item \texttt{\#include <iostream>} 在哪一阶段处理？为什么行末没有分号？
  \item \texttt{int main()} 的名称、圆括号、花括号和返回状态分别承担什么职责？
  \item \texttt{std::cout << "text\textbackslash n";} 中，\texttt{std::}、\texttt{<<}、引号、转义和分号分别表示什么？
  \item 单条 \texttt{g++} 命令隐藏了哪些阶段？\texttt{-c} 为什么能隔开编译与链接？
  \item 缺分号、缺定义和状态 2 分别在哪个阶段失败？每种修复应改变什么？
  \item CMake 的源目录和构建目录为什么应分开？怎样证明一次构建是干净的？
  \item Windows 与 Linux 主线最值得记录的三个命令差异是什么，哪些心智模型不变？
\end{enumerate}

编码任务：

\begin{enumerate}
  \item 从空目录重建两个文件，先用 GCC 单文件命令得到 \texttt{quant-cpp-ready}，再用 CMake 在全新 \path{build/} 中得到同样结果。
  \item 依次运行三个故障实验，为每个实验记录失败命令、阶段、非零状态、稳定诊断类别、根因和恢复步骤。
  \item 在第一个程序中分别增加一行 \texttt{//} 注释和一段不嵌套的 \texttt{/* ... */} 注释，证明输出完全不变；再故意删除输出语句的分号并恢复。
\end{enumerate}


\section{本章小结}

第一个 C++ 程序已经建立最小闭环：头文件提供声明，\texttt{main} 提供入口，花括号和分号构成语法结构，标准流产生可观察输出，状态码向环境报告成功或失败。GCC 把源码经过预处理、编译和链接变成可执行文件，CMake 则把同一目标描述为可重复的目录外构建。诊断时不要只读最后一行错误：先确认停在哪条命令、是否已有目标文件、是否已有可执行文件、程序是否已经启动，再处理该阶段的首个根因。
